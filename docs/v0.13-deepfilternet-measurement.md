# DeepFilterNet3 against RNNoise: measurement (GEL-28, step 1)

GEL-28 adds DeepFilterNet3 as a "Strong" noise filter only if it is clearly
better than RNNoise, the filter the app uses now. This is the first step: an
offline comparison on a fixed set of clips, plus CPU time and delay on one
machine. The harness and the raw results are in
[`v0.13-deepfilternet/`](v0.13-deepfilternet/). Every number below comes from
that harness. Anything not listed as measured was not measured.

## Result

DeepFilterNet3 (DFN3) rates better than RNNoise in 25 of the 30 noisy clips
on DNSMOS OVRL and in 27 of 30 on SI-SDR. The difference depends a lot on the
metric:

| Mean over all noisy clips | Unprocessed | RNNoise | DFN3 | DFN3 − RNNoise |
|---|---:|---:|---:|---:|
| DNSMOS P.835 OVRL | 2.62 | 3.05 | 3.17 | +0.12 |
| DNSMOS P.835 SIG | 3.37 | 3.43 | 3.47 | +0.05 |
| DNSMOS P.835 BAK | 2.95 | 3.83 | 4.00 | +0.17 |
| Personalized DNSMOS OVRL | 2.80 | 3.14 | 3.49 | +0.35 |
| Personalized DNSMOS BAK | 2.41 | 3.33 | 3.86 | +0.53 |
| SI-SDR (dB) | 4.4 | 8.3 | 12.6 | +4.3 |

By noise type:

| Condition | DNSMOS OVRL RNNoise / DFN3 | Personalized OVRL RNNoise / DFN3 | SI-SDR (dB) RNNoise / DFN3 |
|---|---|---|---|
| clean speech | 3.43 / 3.45 | 4.12 / 4.20 | – |
| keyboard, 0 dB SNR | 2.89 / 3.12 | 2.97 / 3.71 | 7.4 / 12.0 |
| keyboard, 10 dB | 3.19 / 3.38 | 3.49 / 4.06 | 12.6 / 16.9 |
| mouse clicks (synthetic), 0 dB | 3.30 / 3.35 | 3.87 / 4.06 | 9.3 / 20.6 |
| mouse clicks (synthetic), 10 dB | 3.42 / 3.42 | 3.92 / 4.20 | 15.0 / 24.1 |
| fan, 0 dB | 2.98 / 3.04 | 3.26 / 3.39 | 6.2 / 9.0 |
| fan, 10 dB | 3.23 / 3.28 | 3.85 / 3.90 | 12.2 / 16.1 |
| TV across the room, 0 dB | 2.65 / 2.83 | 2.22 / 2.66 | 0.9 / 5.1 |
| TV across the room, 10 dB | 3.17 / 3.35 | 3.62 / 3.75 | 10.9 / 12.6 |
| second voice, 0 dB | 2.79 / 2.87 | 2.14 / 2.51 | −1.1 / −1.2 |
| second voice, 10 dB | 2.87 / 3.07 | 2.04 / 2.67 | 9.6 / 10.7 |
| reverberant room | 2.11 / 2.83 | 3.08 / 3.70 | – |

All tables, including SIG and BAK per condition and the unprocessed
baseline: [`results/summary.md`](v0.13-deepfilternet/results/summary.md).
Per clip: [`results/scores.json`](v0.13-deepfilternet/results/scores.json).

What this shows:

- **Keys and clicks while someone talks**, the case GEL-28 is about: DFN3
  removes clearly more of them. Personalized DNSMOS BAK goes from 3.4–3.6 to
  4.3–4.5 for the keyboard; SI-SDR rises by 4 to 5 dB for the keyboard and
  by 9 to 11 dB for the synthetic clicks. Standard DNSMOS OVRL moves only by
  about 0.2 for the keyboard and by 0.05 or less for the clicks.
- **A second voice is not removed by either filter.** At 0 dB, SI-SDR stays
  at about −1 dB for both, the same as unprocessed. Personalized DNSMOS BAK
  rises from 1.7–1.8 (RNNoise) to 2.2–2.4 (DFN3), which is still poor. Both
  models keep speech, whoever speaks; removing other talkers needs a
  speaker-conditioned model, which is outside this issue.
- **Reverberant room:** RNNoise leaves the reverb as it is (OVRL 2.11 against
  2.17 unprocessed); DFN3 reduces it (2.83).
- **Clean speech** is not damaged by either filter (SIG 3.63 and 3.65 against
  3.61 unprocessed).
- On standard DNSMOS OVRL, the mean difference is 0.12. That is small next
  to the 0.43 RNNoise gains over unprocessed audio.

### libDF's default thresholds make DFN3 worse than RNNoise

libDF skips model stages depending on its local SNR estimate. Its library
defaults (`RuntimeParams::default()`, also the LADSPA plugin's defaults:
−10/30/20 dB) skipped the deep-filter stage or the whole model in 43 % of
the 10 ms blocks here, and the result rates worse than RNNoise on every
aggregate: DNSMOS OVRL 2.56, SIG 2.93, SI-SDR 5.2 dB (column "DFN3, libDF
default thresholds" in `summary.md`). The `deep-filter` command line's
thresholds (−15/35/35 dB) ran the full model on every block and give the
results above. An implementation has to set the thresholds explicitly and
budget CPU for the full model.

## Delay

Measured by cross-correlating input and output of the three clean clips:

| Filter | Delay |
|---|---|
| RNNoise v0.2 | 960 samples = 20 ms (all three clips) |
| DeepFilterNet3 | 1440 samples = 30 ms (all three clips); libDF's own figure is the same: STFT 960 − 480 plus 2 hops of look-ahead |

So DFN3 adds **10 ms** over RNNoise, not the 30 ms estimated in the issue.
In the web client both run in an AudioWorklet that reblocks the browser's
128-sample quanta into 10 ms frames, which adds another 10 ms to either one
(`web/scripts/audio/README.md`). Capture, codec, network and playout
buffering are not included.

## CPU on this machine

Measured on the machine that ran the harness: a KVM virtual machine with 8
vCPUs of an AMD EPYC 9354P (server CPU), Linux 6.12, Node 26.13.1, Rust
1.100.0. **This is not a desktop PC, a laptop or a phone.** Other jobs ran
on it at the same time (load average 13 to 15 during the run, see
[`results/machine.txt`](v0.13-deepfilternet/results/machine.txt)), so wall
times have long tails; the thread CPU time is not affected by other
processes taking the core, but shared caches still are.

Per 10 ms block (480 samples at 48 kHz), one thread, over all 36 clips
(41,064 blocks):

| Filter and build | Thread CPU mean | Share of one core | Wall median | Native thread CPU p99 |
|---|---:|---:|---:|---:|
| RNNoise, the app's `rnnoise.wasm`, V8 | 0.42 ms | 4.2 % | 0.41 ms | – |
| RNNoise, native (libwebrtc package clang, `-O3`, as the desktop app builds it) | 0.18 ms | 1.8 % | 0.17 ms | 0.34 ms |
| DFN3, wasm32 `+simd128`, V8 | 1.92 ms | 19.2 % | 1.85 ms | – |
| DFN3, native (tract, x86-64) | 0.65 ms | 6.5 % | 0.63 ms | 1.23 ms |
| DFN3, native, libDF default thresholds | 0.49 ms | 4.9 % | 0.53 ms | 1.06 ms |

An earlier run of the same harness on the same machine, under similar load,
measured 0.40 / 0.17 / 1.79 / 0.56 / 0.45 ms thread CPU mean in the same
order; expect about ±15 % between runs here.

So DFN3 costs about 3.6 times RNNoise natively and 4.6 times in WebAssembly.
V8 here is Node's, not a browser's: an AudioWorklet adds the browser's own
scheduling, which this does not measure. The WebAssembly build is the
harness's own (`dfn-wasm/`, a few C-ABI exports around libDF, no
wasm-bindgen); its output matches the native build within 1.4e-5.

Other costs seen in the harness:

- Building the DFN3 model (`DfTract::new`) took 0.3 to 0.7 s natively and
  0.4 to 0.75 s in WebAssembly per start. It has to happen before or beside
  the audio thread, not in it.
- Sizes: the model archive is 7.98 MB; the WebAssembly module with tract is
  13.5 MB (the app's `rnnoise.wasm` is 5.6 MB).

## Not measured

- **Laptop (Intel Arc) and mid-range Android phone in the PWA:** CPU and
  delay need Rafi's devices. Not done.
- **Listening:** not done. The harness writes every processed clip to
  `work/out/` for it.
- **In a browser:** no AudioWorklet run; the WebAssembly numbers are V8 in
  Node.
- **DNSMOS P.808** (the fourth DNSMOS score): not computed, it needs
  librosa's mel spectrogram. The issue asks for P.835.
- **Real mouse recordings:** no openly licensed one could be fetched without
  a login, so the mouse condition is synthetic (below).

## Decision for step 2

Step 2 (the Strong level) is **not implemented in this change.** The
measured quality difference is large on the metrics that count noise during
speech (personalized DNSMOS, SI-SDR), but small on standard DNSMOS OVRL, and
it has not been confirmed by listening. The costs are 10 ms more delay and,
in WebAssembly, about a fifth of a server core per call; on a mid-range phone
that share will be several times higher and is unmeasured.

What step 2 needs before it starts:

1. Listening to the `keyboard`, `tv` and `second-voice` outputs (`work/out/`).
2. CPU per block on the Intel Arc laptop (native and in the browser) and on
   the Android phone in the PWA, with `run.sh` and `dfn-wasm.mjs` as they
   are.
3. If both hold up, the implementation keeps to the measured setup: the
   full model (thresholds set explicitly, not libDF's defaults), DeepFilterNet
   source and model pinned by commit and SHA-256 as in `fetch.sh`, the
   WebAssembly module and model self-hosted with an integrity hash like
   `rnnoise.wasm`, model built off the audio thread, and the fallback to
   Standard when a device cannot keep up.

## Method

### Clips

36 clips, 10.6 to 12.6 s each, built by `mix.mjs` from the files below. The
clips are not checked in; `run.sh` rebuilds the same ones.

- **Talkers:** three clean speech files from MS-SNSD `clean_test`: m1
  (`clnsp0`, male), f1 (`clnsp2`, female), m2 (`clnsp6`, male), picked by
  estimated pitch. Each at −26 dBFS active speech level.
- **Conditions** per talker: clean; five noises at 0 dB and 10 dB SNR;
  reverberant room. 3 × (1 + 5 × 2 + 1) = 36.
  - keyboard: MS-SNSD `noise_test/Typing_1.wav` (Freesound, CC0), from 20,
    60 or 100 s.
  - mouse clicks: **synthetic**, press and release transients of 3 ms
    decaying noise, high-passed at 1.5 kHz, every 0.25 to 1.25 s.
  - fan: MS-SNSD `noise_test/AirConditioner_1.wav` (Freesound, CC0).
  - TV across the room: another talker (`clnsp12`) through a small
    loudspeaker (200 Hz to 5 kHz) and the simulated room below.
  - second voice: another talker of the other sex, dry (`clnsp13` for m1
    and m2, `clnsp8` for f1).
  - reverberant room: the talker convolved with DeepFilterNet's simulated
    room impulse response (RT60 0.79 s), no added noise.
- SNR uses the active speech level for the target, the TV and the second
  voice, and the RMS for the other noises.
- Every clip gets a −75 dBFS full-band noise floor, like a microphone's own
  noise: the MS-SNSD files are 16 kHz, upsampled to 48 kHz, and would
  otherwise be silent above 8 kHz.
- Clips whose peak would exceed 0.89 are scaled down with their reference
  (`peakGainDb` in `work/clips/manifest.json`).

The MS-SNSD sources are 16 kHz. Both filters run at 48 kHz and DNSMOS scores
at 16 kHz, so the score sees the same band either way, but the filters never
had real content above 8 kHz to work on.

### Filters

- **RNNoise:** the web client's own `web/public/audio/rnnoise.wasm`
  (SHA-256 checked against `RNNOISE-PROVENANCE.json`), driven like the
  worklet: 480-sample frames scaled to 16-bit range, a fresh instance per
  clip. The quality scores use this output. The native build
  (`rnnoise-native.c`, same source commit and model as
  `desktop/native/CMakeLists.txt`) is timed too; its output differs from the
  WebAssembly one by at most 0.0044.
- **DeepFilterNet3:** libDF with tract at the pinned commit, built by
  `dfn-bench/` (native) and `dfn-wasm/` (wasm32), one 480-sample hop per
  call, a fresh model per clip, attenuation limit 100 dB (no limit), no post
  filter. Two threshold settings, see above.

### Scores

- **DNSMOS P.835** (`dnsmos.mjs`): Microsoft's `sig_bak_ovr.onnx` run in
  onnxruntime-node 1.31.1, following `dnsmos_local.py` at the pinned commit:
  16 kHz, 9.01 s windows hopped by 1 s, the non-personalized polynomial
  mapping, mean over windows. One deviation: the 48→16 kHz resampling is the
  harness's own Kaiser-windowed sinc filter, not librosa's, so scores can
  differ from the Python script in the second decimal.
- **Personalized DNSMOS:** the same with `pDNSMOS/sig_bak_ovr.onnx` and its
  mapping. It is trained to count interfering talkers as noise.
- **SI-SDR** against the dry talker at 48 kHz, output shifted back by the
  measured delay, the first 0.5 s skipped. Not computed for the clean and
  reverberant clips.

## Reproduce

Needs curl, Node ≥ 22, Rust and a C compiler; for the WebAssembly timing
also `rustup target add wasm32-unknown-unknown`. No Python or Docker.

```sh
cd docs/v0.13-deepfilternet
# Optional: build native RNNoise with the desktop app's compiler.
export GELABBER_LIBWEBRTC_DIR=/path/to/libwebrtc/pkg
./run.sh
```

`run.sh` fetches and checks the sources into `work/` (ignored by git), builds
the three benches, mixes the clips, runs the filters one after another,
scores them and writes `results/`. The quality results are deterministic;
CPU numbers depend on the machine and its load. On another device, compare
`results/cpu-*.json` with the ones checked in here.
