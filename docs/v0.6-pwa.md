# v0.6: Gelabber vom Handy-Browser installieren

Die Web-App enthält ein Manifest mit stabiler App-ID `/`, Startadresse `/`,
Scope `/`, eigenem Namen, 192/512-px-Icons und einem separaten maskierbaren
Icon. `display: standalone` öffnet sie vom Startbildschirm ohne Browserleiste.
Apple-Metadaten und ein 180-px-Touch-Icon ergänzen die iOS-Installation.
Die Anmeldung verwendet weiterhin die vorhandene Session; durch die
Installation wird kein neuer Account angelegt. Browser und installierte App
können je nach Plattform getrennte Sitzungen haben.

## Installation

- **Android:** Gelabber über HTTPS in Chrome öffnen. Auf der Anmeldeseite oder
  unter **Einstellungen → App installieren** den Knopf benutzen, sobald Chrome
  die Installation anbietet. Alternativ im Browsermenü **App installieren**
  bzw. **Zum Startbildschirm hinzufügen** wählen. Die Verfügbarkeit hängt vom
  Browser und dessen Installationskriterien ab; der Knopf erzwingt keine
  Browserfreigabe und erscheint nicht automatisch auf jeder Plattform.
- **iPhone/iPad:** In Safari **Teilen → Zum Home-Bildschirm** wählen,
  **Als Web-App öffnen** aktivieren, falls angeboten, und **Hinzufügen** antippen.
  Dafür zeigt die App die Anleitung statt eines nicht unterstützten nativen
  Installationsdialogs. Auch iPads mit Desktop-User-Agent werden erkannt.
- Nach dem Start vom App-Icon erscheint kein erneuter Installationsknopf.
  Der native Tauri-Client erhält weder PWA-Installationsoberfläche noch Worker.

Auf echten Handys ist HTTPS mit einem vom Gerät akzeptierten Zertifikat nötig.
Eine HTTP-LAN-Adresse wie `http://192.168…` reicht nicht; die bestehende lokale
HTTP-Compose-Konfiguration ist deshalb kein Handy-PWA-Test. Der HTTPS-Host muss
Manifest, Icons, Worker und Frontend auf derselben Origin unter `/` ausliefern.
Die HTTPS-Konfiguration ist in `deploy/README.md` beschrieben.

## Offline und Updates

Der Produktionsbuild registriert `/sw.js` nach dem Laden der Seite. Der Worker
speichert ausschließlich `/offline.html` in seinem eigenen Cache. Er behandelt
nur GET-Navigationen zu bekannten App-Seiten, einschließlich Kanal-/DM-Links.
API, WebSocket, Medien, Anhänge, Audio-DSP und JS/CSS bleiben auf dem Netzwerk.
Bei einem Verbindungsfehler erscheint eine eigenständige Offline-Seite mit einem
Link zum erneuten Verbinden. HTTP-Fehler des Servers bleiben sichtbar.
Chat und Gespräche benötigen eine Verbindung; Offline-Schreiben oder Web Push
sind nicht Teil dieser Funktion. Das mobile Betriebssystem kann Anrufe im
Hintergrund unterbrechen, auch wenn die PWA installiert ist.

Neue Worker warten auf das Schließen bestehender Tabs/App-Fenster. Kein
`skipWaiting`, keine erzwungene Neuladung während eines Gesprächs und kein
gecachter alter App-Shell. Bei Änderungen an der Offline-Seite muss auch die
Cache-Version in `public/sw.js` steigen. Die Aktivierung löscht nur alte
`gelabber-pwa-offline-*`-Caches, keine anderen Browserdaten. In der Vite-Entwicklung
wird kein Worker registriert; für den PWA-Test den Produktionsbuild verwenden.
Nginx liefert Manifest und Worker ohne dauerhaften Browsercache und mit dem
richtigen Inhaltstyp; fehlende Icons liefern 404 statt der SPA-Seite.

## Prüfen

```bash
cd web
npm ci
npm run lint
npm test
npm run build
# Produktions-Nginx mit genau dem gebauten Client bereitstellen:
docker run -d --name gelabber-pwa-test -p 127.0.0.1:4173:80 \
  -v "$PWD/dist:/usr/share/nginx/html:ro" \
  -v "$PWD/nginx.conf:/etc/nginx/conf.d/default.conf:ro" \
  nginx:1.31.5-alpine
# Chromium vorher mit `npx playwright install chromium` installieren.
npm run test:pwa-smoke
docker rm -f gelabber-pwa-test
```

`GELABBER_PWA_URL` kann den lokalen Testserver überschreiben;
`GELABBER_PWA_BROWSER_EXECUTABLE=/usr/bin/chromium` verwendet vorhandenes
Chromium. Für die Header-/404-Prüfungen des Smoke-Tests den Produktions-Nginx
mit `web/dist` und `web/nginx.conf` auf Port 4173 verwenden; Vite Preview
verifiziert diese Nginx-Eigenschaften nicht. Der Smoke-Test verwendet isolierte
API-Fixtures und legt keine echten Accounts an. Er prüft den realen
Chromium-Manifest-Parser, Icons, den realen Worker, Offline-Navigation und
Wiederverbindung. Die Chromium-Installationskriterien werden geprüft; nur die
Sperre durch das isolierte Inkognito-Testprofil ist dabei ausgenommen.
Installationsdialog-Ereignisse und Standalone-Modus sind
synthetisch; iPhone-Abmessungen/Anleitung sind Chromium-Emulation.

Vor der Freigabe auf echten Android-/iOS-Geräten über HTTPS prüfen: Installation
aus dem Browser, App-Name/-Icon und Start ohne Browserleiste, Login/Logout,
Kanal-/DM-Navigation, Tastatur und Gerätesafearea, erneuter Start nach Offline,
Mikrofonfreigabe und Anruf nach Rückkehr aus dem Hintergrund. Das automatische
Smoke-Ergebnis ersetzt diese Geräteprüfungen nicht.

Die Vorbereitung basiert auf der veröffentlichten Linie v0.5.1. Lokal bestanden
Lint, TypeScript-/Produktionsbuild und alle 546 Frontend-Tests einschließlich
der neuen Installations-/Worker-Tests. Der Browser-Smoke bestand gegen den
Produktions-Nginx mit System-Chromium: Manifest/Icons und Auslieferungsheader,
Installationsereignisse, echte Offline-Navigation/Wiederverbindung, iPhone-Hinweise,
Standalone-Erkennung und die Einstellungsnavigation. Die Geräteprüfungen oben
bleiben vor einer Freigabe auszuführen.
