# v0.6: installing Gelabber from a phone's browser

UI labels below are quoted as the app shows them (German).

The web app contains a manifest with the stable app ID `/`, start URL `/`,
scope `/`, its own name, 192/512 px icons and a separate maskable icon.
`display: standalone` opens it from the home screen without a browser bar.
Apple metadata and a 180 px touch icon complete the iOS installation.
Sign-in keeps using the existing session; installing creates no new account.
Browser and installed app can have separate sessions depending on the
platform.

## Requirement: HTTPS

On a phone the PWA works only over HTTPS with a certificate the device
accepts. Without HTTPS there is no secure context there, and so no service
worker, no install offer, no microphone and no notifications.

**The default Compose configuration is not enough for this.** `docker compose up`
starts Caddy with `auto_https off` on port 80, that is HTTP only. That is
enough for `http://localhost` on the same machine, but not for a LAN address
like `http://192.168…` on the phone. Phones need a TLS endpoint in front:
either your own reverse proxy with a certificate in front of the bundled Caddy,
or the template `deploy/compose/Caddyfile.homelab`; `deploy/README.md`
describes both. With a local CA (`.home.arpa`) every phone must trust that CA.
The HTTPS host must serve manifest, icons, worker and frontend on the same
origin under `/`. No ready-made TLS variant of the Compose file is included.

An access proxy in front that lets every path through only with its cookie
(Authelia, Authentik, oauth2-proxy, Cloudflare Access) is possible: the page
requests the manifest with cookies (`crossorigin="use-credentials"`). Without
that attribute a browser leaves the cookies off the manifest request, the
proxy answers with its login page, and there is no install offer.

## Installation

- **Android:** open Gelabber over HTTPS in Chrome. On the login page or under
  **Einstellungen → App** (Settings → App), use the **App installieren**
  (install app) button as soon as Chrome offers the installation. Until then
  the page names the way through the browser menu (**App installieren** or
  **Zum Startbildschirm hinzufügen**). Availability depends on the browser and
  its install criteria; the button does not force the browser's approval and
  does not appear automatically on every platform.
- **iPhone/iPad:** in Safari choose **Teilen → Zum Home-Bildschirm**
  (Share → Add to Home Screen), turn on **Als Web-App öffnen** (open as web
  app) if offered, and tap **Hinzufügen** (Add). For this the app shows the
  steps instead of an unsupported native install dialog. iPads with a desktop
  user agent are recognised too.
- **Desktop browsers:** the login page shows the install hint only when the
  browser actually offers the installation (Chrome, Edge). Under
  **Einstellungen → App** the hint is always there, without phone wording.
- Inside the installed app no install UI appears any more, neither on the
  login page nor in the settings. A normal browser tab cannot tell whether
  Gelabber is already installed; the hint stays visible there. The native
  Tauri client gets neither the PWA install UI nor the worker.
- Over plain HTTP the login page on a phone says that HTTPS is needed.

## Appearance on the phone

`theme-color` follows the account theme (light, dark, system and custom
themes): a script in `index.html` sets the colour from the paint cache before
the first frame, `theme/theme.ts` on every theme change. Android uses it to
colour the status bar and the app overview. The colours in the manifest stay
fixed; they only affect the splash screen on opening. The viewport uses
`viewport-fit=cover` (required for the safe area insets) and
`interactive-widget=resizes-content` (Chrome on Android shrinks the layout
with the keyboard; Safari ignores the key).

## Offline and updates

The production build registers `/sw.js` after the page has loaded. The worker
stores only `/offline.html` in its own cache. It handles only GET navigations
to known app pages, channel/DM links included. API, WebSocket, media,
attachments, audio DSP and JS/CSS stay on the network. On a connection error a
self-contained offline page appears at the requested address, in the colours
of the last used theme. **Erneut verbinden** (reconnect) reloads exactly this
address; an invite, channel or login link is not lost. When the browser
reports a connection again, or when you return to the page while connected, it
reloads by itself. HTTP errors from the server stay visible; 502/503/504
during a server restart are not replaced by the offline page either. Chat and
calls need a connection; writing offline is not part of this feature. The
mobile operating system can interrupt calls in the background even when the
PWA is installed.

New workers wait until existing tabs/app windows are closed. No `skipWaiting`
and no forced reload during a call. When the offline page changes, the cache
version in `public/sw.js` must go up as well; `src/pwa/worker.test.mjs` fails
otherwise. The same test requires the worker to know every route from
`src/routes.tsx` as an app page (`APP_PAGE`): a new route would otherwise get
no offline page and would not be a target for tapping a notification.
Activation deletes only old `gelabber-pwa-offline-*` caches, no other browser
data. No worker is registered in Vite development; use the production build
for the PWA test.

The worker stores no app shell. The browser's HTTP cache did so anyway up to
v0.5.x: Nginx served `index.html` without `Cache-Control`, so browsers kept it
fresh for up to days depending on the build's age, and missing `/assets/*`
files were answered with the app shell. After a server update an installed app
started with the old shell and could stay blank (reproduced in Chromium; the
same is to be assumed for the desktop app's WebView). `web/nginx.conf` now
sets:

- `index.html` and every app route (SPA fallback): `Cache-Control: no-store`.
  The browser does not keep the shell and fetches it from the server on every
  load (a good 1 kB compressed). `no-cache` is not enough: when Chromium
  restores a tab on start, brings back a discarded tab, or you go back to the
  app, it takes a stored copy without asking. After an update the old client
  then started from its still stored `/assets/*` files, again on each of these
  loads. Side effect of `no-store`: the page does not enter the back/forward
  cache; going back to the app reloads it.
- `/assets/*` (hashed file names): one year `immutable`; a missing file is a
  404 and never the app shell. The same 404 applies to `/icons/`, `/audio/`
  and `/images/`.
- Manifest, worker and offline page: `no-cache` and the right content type.
- gzip for HTML, JS, CSS, JSON and the manifest.

This applies to every shell a v0.6 server has served. **On an upgrade from
0.5.x it does not take effect yet:** a shell loaded there sits in the browser
without `Cache-Control`, and the new header reaches it only when the browser
asks again. A client that had opened Gelabber in the days before the upgrade
can therefore start once more with the old shell: either the old client runs
from the cache, or the page stays blank because its files no longer exist. A
restored tab, a brought-back discarded tab and going back take the old shell
regardless of its age, so even weeks later. Reloading once fixes this for
good: the new response replaces the stored shell (reproduced in Chromium; the
same is to be assumed for the 0.5.x desktop app's WebView, but not checked
there).

An app that stays open across a server update keeps running the old client
until the next reload; there is no new-version hint yet. If such an old client
only then loads a part of the program (for example the emoji picker), it gets
a 404 until the app is reloaded.

The bundled Caddy and the homelab template compress responses
(`encode zstd gzip`, important for the API's JSON responses) and hand `Host`
on to the services with its port (`{hostport}`). With `{host}` every WebSocket
handshake failed with 403 as soon as Gelabber ran on a non-default port. The
API compares `Origin` and `Host` without the scheme's default port: a proxy in
front that writes out the default port (`Host: example.com:443` for HTTPS,
`:80` for HTTP) works as under 0.5.x.

**Check on upgrade:** any other port in `Host` must now be the browser's. A
proxy in front that writes in a port the browser does not use (Nginx with
`proxy_set_header Host $host:$proxy_port;`, or `$host:$server_port` behind a
port translation like 443 → 8443) worked under 0.5.x because Caddy cut the
port off. With the v0.6 Caddyfile, `/ws` answers it with 403: chat no longer
updates and voice does not connect, while login and the REST API keep working.
Remedy on the proxy in front: `proxy_set_header Host $http_host;`. Details are
in `deploy/README.md` under "Existing Caddy".

The new Caddyfile takes effect only when the checkout contains it and the
proxy container has been restarted; switching the images alone leaves the old
one in force, and a `caddy reload` is not enough. On a rollback to 0.5.x the
old Caddyfile belongs to the set. `deploy/README.md` describes both under
"Rollout and rollback with exact digests".

New is the look at the scheme. `Host` does not reveal it, so
`API_COOKIE_SECURE=true` stands for Gelabber running behind TLS: `/ws` then
accepts only pages with an `https://` origin. Up to 0.5.x a page that someone
served under the same host name over `http://` also got a connection, for
example an attacker on the network who answers plain HTTP for the name;
Firefox sends the session cookie along on such a request, Chromium does not.
`http://localhost`, `127.0.0.1` and `[::1]` stay allowed, because browsers
accept `Secure` cookies there as well. Without `API_COOKIE_SECURE` (running
over plain HTTP) nothing changes.

## Notifications

Mobile browsers allow no notification directly from the page
(`new Notification()` fails there). When the worker is active, the app
therefore shows message notifications through its registration. A tap brings
the running app window to the front and opens the conversation in it without
reloading the page; when no window is open any more, the worker opens one on
the conversation. Without a worker (Vite development, desktop app, HTTP) the
previous way through the page stays.

A notification also disappears without a tap as soon as its conversation is
open in a visible app window, for example after returning through the app
overview. On logout all of the account's notifications disappear. An app
window that only starts or reloads leaves the other conversations'
notifications in place.

While a conversation is open in a visible app window, no new notification is
raised for it either. That holds across windows: every window of an account
gets the same messages and decides by its own visibility, so this includes
the browser tab left behind in the background after installing. The windows
coordinate through Web Locks; a visible window holds a lock for its
conversation, and whoever wants to show a notification in the background
checks first. Showing, listing and closing run one after another per account,
under a second lock. That way a window coming on screen also clears what
another one is showing right now. Without it Chromium also loses a
notification that one window shows while another lists them: it is missing
from every list afterwards (reproduced with Chromium 153).

A window in the background still announces messages from other conversations,
even when another window is visible and shows them there as an in-app hint.

On a phone a notification comes with sound and vibration, as the device is set
up for the page or the installed app. Gelabber has no message sound of its
own; silent, as it was and stays on the desktop, it would be just an icon in
the status bar while in a pocket. A further message in the same conversation
replaces the notification and announces itself again (`renotify`), at most
every five seconds per conversation; a message that went unannounced only
because its conversation was visible in another window does not count. Gelabber
has no switch for this; you silence them in the device's notification
settings. A device counts as a phone when it identifies as Android, iPhone or
iPad. When several of the account's windows are in the background, only one
shows the message, so that it is not announced twice.

Permission is requested only through a button or switch in
**Einstellungen → Benachrichtigungen** (Settings → Notifications). The setting
is off by default.

**Web Push is not part of v0.6.** A notification is raised only while the app
is still running in the background and keeps its connection, for example
during a call or shortly after switching to another app. When the app is
closed or suspended by the operating system, nothing arrives. The settings
point this out on phones. On iPhone and iPad the Notifications API exists only
in the installed app (from iOS 16.4), not in a Safari tab.

## Checking

```bash
cd web
npm ci
npm run lint
npm test
npm run build
# Serve exactly the built client with the production Nginx:
docker run -d --name gelabber-pwa-test -p 127.0.0.1:4173:80 \
  -v "$PWD/dist:/usr/share/nginx/html:ro" \
  -v "$PWD/nginx.conf:/etc/nginx/conf.d/default.conf:ro" \
  nginx:1.31.5-alpine
# Install Chromium first with `npx playwright install chromium`.
npm run test:pwa-smoke
docker rm -f gelabber-pwa-test
```

`GELABBER_PWA_URL` can override the local test server (loopback only);
`GELABBER_PWA_BROWSER_EXECUTABLE=/usr/bin/chromium` uses an existing
Chromium. The smoke test needs the production Nginx with `web/dist` and
`web/nginx.conf`; Vite preview lacks these headers. To check a second
deployment it briefly swaps the build in `web/dist` and restores it; when the
test server serves another directory, `GELABBER_PWA_DIST` names it. The test
uses isolated API fixtures and creates no real accounts. It checks:

- the Nginx headers: app shell `no-store`, assets `immutable` and gzip, 404 for
  missing files, content types of manifest and worker, a small favicon;
- the real Chromium manifest parser, the icons and the install criteria (only
  the block caused by the isolated incognito test profile is exempt);
- manifest and install criteria behind an access proxy that requires its
  cookie on every path (a stand-in in the test, no real Authelia or similar);
- the real worker: offline navigation to a deep link with a query, the offline
  page in the app's theme, reloading the same address, and the automatic
  reload on the `online` event;
- the install UI on Android, iPhone, desktop and in the installed app;
- `theme-color` for light, system and a custom account theme, also before the
  app starts;
- the path of a message from the gateway to the notification through the
  worker registration with the app in the background, on the emulated phone
  with sound (`silent: false`, `renotify: true`) and shown only once with two
  windows in the background, and what removes it again: a second window
  starting or reloading does not, the conversation opened visibly and logging
  out do; also that a second window in the background announces nothing the
  front one is showing, and announces the next message as soon as the front
  one has left the conversation;
- the path from tapping a notification to the conversation;
- a second deployment with new asset names in a real browser profile with HTTP
  cache: going back to the app and the next start load the new shell. Going
  back stands for the loads that take a stored copy without asking. The tab
  restored after a browser start and the brought-back discarded tab are not
  in the smoke; both were reproduced by hand with Chromium 152 and load the
  new shell.

Synthetic in this are the install dialog events, standalone mode and the
notification's tap event (a script event does not count as a user action for
the browser; focusing the window and opening a new window therefore run only
in the unit tests against stand-ins). The gateway and the access proxy are
stand-ins in the test, and going to the background is reported to the page by
script, because headless Chromium never hides a page. Whether a notification
makes a sound, the test reads from its options; nothing is heard. iPhone
dimensions and steps are Chromium emulation.

The smoke test does not run in CI. There, checks without a browser cover what
can be checked without one. `npm test` runs `web/src/pwa/nginx.test.mjs` for
the rules in `web/nginx.conf`, `web/src/pwa/shell.test.mjs` for the wiring of
the app shell (manifest link in `index.html`, existing icons in the stated
size, start from `main.tsx`) and `web/src/pwa/start.test.ts` for only the
production build in a browser registering the worker and following a tap on a
notification. `deploy/compose/tests/test_caddy_app_proxy.py` checks the two
Caddyfiles. Whether Chromium accepts manifest and worker is still shown only
by the smoke test.

The browser smoke for video in the desktop app's tiles, which the web client
draws itself since v0.6, also runs only locally:
`npm run test:native-video-smoke`, without a server, in headless Chromium.
What it checks and when it is due is in `desktop/README.md` under "Tests".

## Not checked on real devices

Everything above was checked only with Chromium on Linux, directly against
Nginx and through the bundled Caddy over HTTP on loopback. No real phone, no
Safari/WebKit and no TLS endpoint were involved. To check over HTTPS before
release:

- **Android (Chrome):** install offer after real use, WebAPK or a mere
  shortcut (especially with a local CA), app name/icon, start without browser
  bar, colour of status bar and app overview with the light and a custom
  theme, keyboard and input field, notification with the app in the
  background with sound and vibration, also for the second message in the
  same conversation, including the tap (window to the front, right
  conversation, new window after closing, other notifications stay),
  notification disappearing after returning through the app overview, no
  notification for the conversation open in the app while a Chrome tab with
  Gelabber is open next to it, start without connection and return, return to
  app and tab after a server update once Android had ended them in the
  background (new shell; reproduced only for Chromium on the desktop).
- **iPhone/iPad (Safari, home screen app):** steps and wording of
  "Zum Home-Bildschirm", look of the status bar (`default`) with a dark app
  theme and light system and vice versa, safe areas in portrait and
  landscape, separate sign-in in the installed app, whether the Notifications
  API is available there and notifications arrive with sound, start without
  connection, behaviour after a server update (the same HTTP cache as in
  Chromium is assumed for WebKit), `online` event after waking up.
- **Both:** login/logout, channel/DM navigation, microphone permission and a
  call after returning from the background.

The automatic smoke result does not replace these device checks.
