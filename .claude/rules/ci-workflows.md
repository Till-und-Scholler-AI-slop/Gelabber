# CI workflows (`.github/workflows`)

Claude Code loads this file when it works on a workflow; AGENTS.md points here for everyone else.

Keep CI lean. Pull requests check only what is needed to merge safely.

- **Pull requests:** fmt, clippy/lint, tests and build of each area they touch, with the integration checks that fit in its jobs: the backend tests against Postgres, Redis and MinIO, the desktop loopback calls and package checks, MinIO's `minio-init` test. The web client runs against a server only in `e2e-extended.yml` (below). Aim for under 15 minutes per workflow with a warm cache.
- **Areas:** five, `backend`, `web`, `desktop`, `deploy` and `minio`. Each top-level folder belongs to its area, and `.github/workflows/scripts/changes.py` adds the files a check of another area reads (the emoji data, the web theme tokens the desktop tests compare, the backend in `deploy`, the MinIO files in `minio`). `ci.yml` runs only the areas a pull request touches, and a push only those its commits touch since the last commit whose push run passed (GEL-360, GEL-363). Each app image builds only when its own inputs change (GEL-391); a file under `.github/` starts the areas whose jobs it runs (GEL-390), and a release or hotfix pull request to `main` runs all, because `main` reuses only such a run. `ci-ok` is the one required check; a new job joins its `needs`, and a new area also gets an output of the `changes` job and an entry in `ci-ok`'s `AREAS`, which fails on any value but `true` or `false` (GEL-397).
- **Inside the backend area** (GEL-393) a pull request to a version branch runs the tests of the crates it changes and of those depending on them (`scripts/rust_tests.py`, a nextest filter); everything runs on pushes, pull requests to `main`, cache key inputs (`tested_tree.py`), `.github/` and whatever the script cannot place. The desktop media tests run one at a time, the others side by side.
- **After merge (push to `main`/`v*`) and releases:** packaging, installers, package repositories, signing and uploads; `desktop-native.yml` packages when its caller sets `package`, and `deploy/compose/tests/test_desktop_native_modes.py` holds what each mode runs (GEL-395). One exception: a release or hotfix pull request to `main` packages its apps unsigned (`candidate`), so that `desktop-release.yml` only signs and attaches them after the tag (`prebuilt_run`, GEL-358). Without such packages from the tag's tree, it builds them.
- **Merge queue:** off (ruleset `Merge queue (version branches)` disabled, GEL-362). `ci.yml` still runs a `merge_group` like a pull request, read-only and without packages, so switching the ruleset on again needs no workflow change.
- **A push to `main`** checks nothing again when the merged pull request's last green run passed the same tree with every area (`scripts/tested_tree.py`, GEL-357); otherwise it runs all (GEL-390). Pushes to `v*` run the areas they touch and save those areas' caches; the others' keys did not change.
- **A test that needs a tool or service** may skip without it only outside CI; with `CI` set (to anything but empty, `0` or `false`) it fails, and the job installs what its tests need (GEL-375). One helper per language decides: `gelabber_testing::missing` (desktop), `requires` and `missing` in `deploy/compose/tests/prerequisites.py` (also loaded by `desktop/packaging/tests`), `missing` in `web/scripts/prerequisite.mjs`. Backend tests do not skip: they need Postgres, Redis and MinIO everywhere.
- **Flaky tests** (GEL-389): nextest profile `ci` (`backend/` and `desktop/.config/nextest.toml`) runs a failed test once more and passes it when the retry passes; `scripts/flaky_tests.py` lists every such test in the job summary, and after a push the `flaky-tests` job adds it to its issue, opening at most three new ones per run; a failed GitHub request there only warns. `.github/flaky-tests.toml` names the issue of known flaky tests, at most five; any other gets an issue "Flaky test: <test>".
- **Extended E2E** (`e2e-extended.yml`: the real app in browsers with the fault matrix, the scenarios, the browser checks against a running app (`npm run test:e2e-server`) and the PWA smoke) runs after pushes to a version branch that touch `backend/` or `web/`, on release and hotfix pull requests to `main`, and by hand. No feature pull request waits for it. After each push run a job of its own opens or comments on the issue "Extended E2E fails on <branch>" when the run is red, and closes it when the run is green again (GEL-378); a pull request and a run by hand show their result only in the run. Such an issue reaches Linear without a project: a maintainer adds it to the project Gelabber with the label Bug.
- **Other manual diagnostics** (soak and stability loops) go in their own workflow, started by hand, outside the PR gate.
- **Lists of scripts** go behind one entry point (e.g. `npm run test:checks`). CI and developers run the same command.
- **Test edits:** the `changes` job lists a pull request's deleted or loosened assertions, skips, raised limits, sleeps, retries and runner changes in its summary and as warnings (`scripts/edited_tests.py`, GEL-387). It never fails the run.
- **New check:** say what it catches that existing checks miss. Add it to an existing job unless a parallel job saves wall time. Remove checks that a new one replaces.
- **Every workflow** sets top-level `permissions`, by default `contents: read`, with jobs adding only what they need. Every job sets `timeout-minutes`. Actions stay pinned to commit SHAs (`deploy/compose/tests/test_workflow_pins.py`). zizmor checks every workflow in the `deploy` job (GEL-361); a finding is fixed, or excepted with its reason in `.github/zizmor.yml` or an inline `# zizmor: ignore[rule]` comment. actionlint, with shellcheck at warning level, checks them in the same job (GEL-383); runner labels it does not know yet go in `.github/actionlint.yaml`. It does not check the names of outputs a `run:` step writes, or the inputs and outputs of actions pinned to a commit SHA.
- **Tokens** (`deploy/compose/tests/test_workflow_tokens.py`): pull-request jobs get read-only tokens. A write runs in a job that pull requests skip (`if:` with `github.event_name != 'pull_request'`). Where fetched code was built in a pull request's run, the write gets a job of its own that runs none of it: `libwebrtc-store.yml`, the `publish` job of `publish-minio.yml`. The one job that builds and writes is `publish` in `publish-images.yml`: it runs only for a passed push run of `main` and builds that commit, code that has landed. A reusable workflow that pull requests call asks for no write, because GitHub checks it against the caller's grant before any `if:`. Checkouts set `persist-credentials: false`. `run:` scripts read `$GITHUB_REF`, `$GITHUB_REPOSITORY` and the like from the environment, not as `${{ github.* }}`.
- **Caches** are saved only by pushes (`save-if`, `cache-to`, `actions/cache/save` behind an `if:`); pull requests only read them, because per-PR copies exceed the repository's cache quota. Two exceptions: the libwebrtc jobs hand their package to the core jobs through the cache (`fail-on-cache-miss`), so a pull request or the merge queue saves it when its key is missing (`test_workflow_caches.py`), and `setup-node` in `e2e-extended.yml` saves the npm cache on its runs for release and hotfix pull requests and by hand. After each push and nightly, `cache-cleanup.yml` deletes such pull-request copies and superseded generations, so a cache key must change when its contents would (Cargo.lock, toolchain, build settings); a core job whose libwebrtc package was deleted between its jobs fails its restore, and the cure is to re-run all jobs, not only the failed ones.
- **Slow build outputs** that the cache quota would evict are kept where nothing evicts them: the libwebrtc packages are assets of the `libwebrtc-packages` release, stored after pushes and releases (`libwebrtc-store.yml`) and fetched on a cache miss (`desktop-native.yml`); the app images' layer cache is each image's `buildcache` tag in the registry, written by `publish-images.yml`.
- **A release build** (`desktop-native.yml` with `release_tag`) builds, packages, makes one loopback call and tests the installed package, but runs the other code checks no more: CI ran them on the same tree, on `main` or in the merged pull request.
- **A release becomes "Latest" last.** `image_set.py` creates it with `--latest=false`; `mark-latest` in `desktop-release.yml` sets the mark once both apps are attached, and never on a release older than the current one.
- **`libwebrtc-packages` and `build-deps` stay pre-releases.** If one became "Latest", `releases/latest/download/latest-native.json` (the apps' updater) and the web client's download links would point at it. A stored libwebrtc package is fetched only when `desktop/native/libwebrtc-packages.sha256` lists its SHA-256.
- **Runners** are named by version, never `-latest`.
- **Comments** in workflows are one or two lines saying why. Longer reasoning and history go in commit messages or `docs/`.
